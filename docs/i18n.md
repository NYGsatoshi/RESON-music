# Internationalization

RESON uses `next-intl` for UI localization.

## Supported locales

- `ja` — default locale
- `en` — English

Message catalogs live in `messages/ja.json` and `messages/en.json`. Keep their key structures identical; CI verifies this through `__tests__/i18n/messages.test.ts`.

The application uses `Asia/Tokyo` as its explicit formatting time zone so server-rendered and browser-rendered dates remain consistent.

## Routing strategy

Locale-aware routing uses a top-level `[locale]` segment with `localePrefix: "as-needed"`:

- Japanese is the default locale and remains prefixless (for example `/login`).
- English uses the `/en` prefix (for example `/en/login`).
- A `/ja` URL is canonicalized back to the prefixless Japanese URL.
- Locale-aware links and routers come from `i18n/navigation.ts`.
- GitHub Pages static preview mirrors the same public URL shape by copying the exported `ja` tree to the output root.

## Translation coverage

The current UI surface is localized across:

- Landing and public privacy information
- Authentication, registration, password reset, and artist registration
- Listener home, library, search, Explore, feed, albums, tracks, playlists, messages, notifications, communities, events, curator/boost rankings, invitations, Wrapped, profile, pricing, parental billing, privacy requests, and settings
- Artist dashboard, upload, reports, supporters, payout/bank-account UI, album/lyrics/ISRC management
- Admin review dashboard and privacy-request administration
- Shared player controls, theme toggle, support/tipping, boost, support graph, payment confirmation, and locale switcher

Landing and the main authentication entry points expose an explicit language switcher. The reset-confirmation screen intentionally does not show a switcher because changing URLs during a password-recovery flow can discard recovery parameters.

## Translation boundaries

Translate product UI, client-side validation copy, navigation, accessibility labels, metadata, dates, numbers, and plan descriptions.

Artist names, track titles, user-generated content, and sample catalog content remain source content unless the data model explicitly stores localized variants.

Prices are stored as numeric values and formatted independently from locale. Selecting English must not implicitly change JPY billing to another currency.

API/database enum values that predate i18n (for example some privacy-setting choices) remain stable storage values. The UI maps those values to localized labels instead of changing persisted data.

Backend/API failures must not be surfaced to users as raw `error` strings or SDK `error.message` values. APIs should return stable machine-readable codes where the UI needs to distinguish failure cases; localized pages map those codes to message-catalog entries and otherwise use a localized fallback. This keeps Japanese and English UI consistent and avoids exposing implementation details.

## Validation

CI covers:

- Japanese/English message key parity
- No raw backend/SDK error messages surfaced from localized pages or shared components
- Locale routing helpers
- Lint and TypeScript typecheck
- Unit tests and Next.js build
- Static Japanese/English preview generation
- Storybook accessibility tests
- Playwright browser tests
